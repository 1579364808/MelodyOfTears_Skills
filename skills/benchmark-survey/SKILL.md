# Benchmark Survey

## Overview

本 Skill 定义了对学术 Benchmark 进行**全面调研**的标准化流程。输入材料包括论文 PDF（必需）、GitHub 仓库（有则更佳）和本地数据目录（可选）。输出是一份结构化的中文 Markdown 调研报告。

报告文件遵循固定命名格式：**`{bench名字}-{作用}-调研报告.md`**，其中：
- `{bench名字}` — Benchmark 的名称缩写（如 `DevOps-Gym`、`PRDBench`、`SWE-bench`）
- `{作用}` — Benchmark 的核心作用/定位，一句话概括（如 `首个端到端DevOps基准测试`、`仓库级代码修复基准测试`）
- 示例：`DevOps-Gym-首个端到端DevOps基准测试-调研报告.md`

报告内容包含 **10 个核心内容块**，实际执行时根据可用材料灵活裁剪——有论文用论文，有仓库看仓库，两个都有就交叉验证。

### 输入材料清单

| 材料 | 必要性 | 主要用途 |
|------|-------|---------|
| 论文 PDF | ✅ 必需 | 提取背景、方法论、评估结果、未来工作 |
| GitHub 仓库 | ⭕ 强烈推荐 | 分析目录结构、阅读源码、确认数据集细节 |
| 本地任务数据目录 | ⭕ 推荐 | 查看实际任务配置、示例、评估脚本 |

### 核心内容块总览

```
┌──────────────────────────────────────────────────────────────────┐
│  §1   Benchmark 背景                                              │
│  §2   数据集介绍                                                   │
│  §3   构建流程与流水线                                               │
│  §4   测评方案与方法                                                │
│  §5   现有模型测评结果                                               │
│  §6   数据进化与扩展想法                                             │
│  §7   仓库/数据集目录结构（含示例）                                    │
│  §8   任务/样本示例                                                 │
│  §9   数据的用途与训练可用性                                          │
│  §10  人工介入与 AI 的分工                                           │
│  §11  用 Benchmark 生成训练数据（可选，仅当管线代码可用时）            │
└──────────────────────────────────────────────────────────────────┘
```

## 详细调研流程

### Step 1: 从论文提取核心信息

论文通常以《标题》或引用格式（如 "Author 等，2026"）被引用。按论文章节依次提取：

#### §1 Benchmark 背景

从 Introduction（引言）和 Related Work（相关工作）中提取：

- **领域背景**：该领域当前的技术背景是什么？存在什么痛点？
- **现有工作的局限性**：已有的数据集/基准测试有什么不足？
  - 覆盖范围窄（只关注单一任务）
  - 数据规模小/多样性不足
  - 评估方式不科学（缺乏自动化、依赖人工）
  - 未考虑特定场景（如动态环境、多步推理等）
- **本 Benchmark 的核心贡献**：解决了上述哪些问题？有什么独特价值？

#### §2 数据集介绍

从 Construction / Dataset 章节提取，用表格呈现：

- **数据规模与分布**：总样本数、各类别数量、涉及项目/领域数量、编程语言等
- **任务类型详解**：每类任务的定义、输入格式、输出格式、典型场景
- **分类/标签分布**：如果有分类体系，展示各类别占比（可引用论文中的图表）
- **数据来源**：真实数据（来自 GitHub、StackOverflow 等）还是人工合成？

#### §3 构建流程

从数据构建方法论章节提取：

- **设计原则**（如有）：真实性、多样性、公平性等
- **数据收集管线**：原始数据如何收集、清洗、标注？
- **质量控制**：如何确保数据质量？人工审核？自动化校验？
- **数据污染/泄露防护**：是否考虑了数据污染问题？如何防止评测作弊？
- **技术挑战与解决方案**：构建过程中遇到的主要困难及应对方式

#### §4 测评方案与方法

从 Evaluation / Experimental Setup 章节提取：

- **评估框架/环境**：评测运行的软件/硬件环境（GPU、Docker、API 等）
- **评测流程**：需要特别说明**谁执行任务、谁评分、评分是否自动**。
  - 结构化展示评估流程，标注人工与自动的边界
- **评估指标**：各任务/类别使用的具体指标。用表格呈现：
  | 任务类型 | 评估指标 | 评分方式 |
  |----------|---------|---------|
  | ... | ... | 自动/人工/混合 |
- **稳定性/公平性保障**：是否做了多次重复运行？结果的标准差/置信区间如何？

#### §5 现有模型测评结果

从 Results 章节提取：

- **整体表现概览**：各模型/方法在各类任务上的表现。用表格呈现。
- **对比分析**：
  - 不同模型系列之间的对比（如 GPT vs Claude vs Llama）
  - 不同规模模型之间的对比（如 7B vs 70B）
  - 不同方法/框架之间的对比
- **错误原因深度分析**（最有价值）：模型为什么失败？常见错误模式有哪些？
  - 可用表格呈现：错误类型、占比、具体表现

#### §6 数据进化与扩展想法

从 Conclusion / Future Work 提取官方方向，并结合自己的推理提出扩展：

- **论文提出的方向**：覆盖面、语言/领域扩展、社区共建等
- **自主扩展思考**（根据不同 Benchmark 类型调整）：
  - 覆盖更多编程语言/自然语言/领域
  - 新增任务类型/更复杂的场景
  - 合成数据增强（组合故障、多模态、长序列等）
  - 评估体系扩展（效率、鲁棒性、公平性、可解释性等）

### Step 2: 从 GitHub 仓库和本地数据提取信息

先全面扫描仓库的目录结构和所有文件，然后深入阅读关键内容。

#### 2.1 全局扫描

```python
# 查看顶层目录，了解整体结构
list_dir(target_directory="<repo_root>")

# 递归获取所有文件概览（使用 search_file 通配）
search_file(pattern="*", recursive=false, target_directory="<repo_root>")
```

#### 2.2 阅读说明文档

- 读取 `README.md` 了解项目简介、安装方式、使用方式、引用格式
- 读取 `requirements.txt` / `package.json` / `Cargo.toml` 等了解依赖
- 如果仓库有论文或文档目录（如 `docs/`、`paper/`），一并读取

#### 2.3 深入探索数据与代码

根据扫到的目录结构，主动深入以下类型的内容：

- **数据/任务目录**：找到存放数据集、任务样本的位置，统计数量和类别，读取代表性样本
- **构建/收集脚本**：找到数据集构建、收集、清洗的代码，分析自动化程度
- **评估工具**：找到评测脚本、打分逻辑、指标计算代码
- **辅助工具**：工具函数、可视化、日志等基础设施

每条路线的深入程度取决于该目录是否存在以及内容体量。

#### §7 目录结构 + §8 任务示例

将探索结果整理为：

- **目录结构树**：用代码块呈现带层次的完整文件结构（选取关键路径，无需全部列完）
- **任务/样本示例**：展示代表性样本的配置、元数据、输入输出格式
- 用实际读取到的代码块展示，让读者直观感受数据

### Step 3: 分析数据用途与分工

基于论文和仓库信息进行推理分析。

#### §9 数据的用途与训练可用性

回答以下问题：

- **数据的直接用途**：
  - 模型/方法评估与排名
  - 错误模式分析与能力诊断（分析哪些场景下模型容易失败）
  - 作为模型微调/训练的监督数据（SFT、RL、DPO 等）
  - 作为能力测试沙盒

- **轨迹/中间数据能否用于训练**：
  - 如果评测过程中记录了模型的中间输出（如执行轨迹、推理链），能否用于后续训练？
  - 用表格对比不同训练范式的可行性：
    | 范式 | 所需数据 | 可行性 | 说明 |
    |------|---------|-------|------|
    | SFT | 成功样本轨迹 | ⭐~⭐⭐⭐ | 取决于正样本数量和多样性 |
    | RL | 评估信号 | ⭐⭐⭐ | 有自动评估脚本则无需人工 |
    | DPO/RLHF | 正负样本对 | ⭐⭐⭐ | 可构建对比对 |
    | Behavior Cloning | 参考轨迹 | ⭐⭐ | 需 Oracle/专家轨迹 |
  - 分析当前限制（成功样本是否稀缺、计算成本等）

#### §10 人工介入与 AI 的分工

结合论文描述和仓库中实际的代码文件，分析整个流程中**哪些部分是人工完成的、哪些由 AI/Agent 执行、哪些已有自动化脚本**。

- 论文中提到"人工完成"的环节 → 人工
- 论文中提到"由模型/Agent 执行"的环节 → AI
- 仓库中有 `.py`/`.sh` 等可执行脚本、有文档说明自动化流程的 → 已有实现
- 论文提到该环节但仓库中找不到对应代码的 → 尚未自动化

### Step 4: 分析 Benchmark 能否用于训练数据合成（新增）

> **适用场景**：当该 Benchmark 不仅提供了评测数据，还提供了**数据生成管线**（代码 + 方法论文），且用户关心"能不能用这个 Benchmark 的方法来生成训练数据"时，必须分析此节。

#### §11 Benchmark → 训练数据合成方案（新增）

回答以下问题：

**A. 厘清核心关系**

| 概念 | 对应什么 | 能否用于训练 |
|------|---------|-------------|
| **Benchmark 的评测数据集** | 这是"考卷"，用来评估模型最终能力 | ❌ 不能直接用来训练（数据污染） |
| **Benchmark 的生成管线** | 这是"出卷子的方法"，可无限生成新数据 | ✅ 能用来生成训练数据 |

**B. 管线代码是否可用**

- 仓库中是否有数据生成/合成的代码？文件路径？
- 是否需要 API Key？需要哪种 LLM？
- 是否可以直接运行（有无 CLI 命令）？

**C. 从评测到训练的数据生产流水线**

用流程图展示如何将生成管线改造为训练数据流水线，格式参考：

```
[生成管线名称]（[CLI 命令/脚本路径]）
  │  输入：可调整的参数（领域、语言、难度、seed 等）
  │  不改管线代码，只改参数
  ↓
生成 N 个全新数据样本（与原评测数据集不同 seed）
  ↓
[可选] 后处理步骤（场景转换、格式适配等）
  ↓
得到训练可用数据（JSON / 轨迹 / 代码库）
  ↓
跑目标模型 → 记录完整交互轨迹
  ↓
按轨迹质量分桶 → SFT / DPO / RL 训练
```

**D. 训练范式可行性矩阵**

| 训练范式 | 所需数据 | 可行性 | 实际操作 |
|---------|---------|-------|---------|
| SFT | 成功样本轨迹 | ⭐~⭐⭐⭐ | 说明如何获取正样本、数量预估 |
| DPO/RLHF | 正负样本对 | ⭐~⭐⭐⭐ | 说明如何构造对比对 |
| RL | 评估信号 | ⭐~⭐⭐⭐ | 是否有自动评估脚本作为 reward |
| Behavior Cloning | 专家轨迹 | ⭐~⭐⭐ | 论文/仓库是否提供参考轨迹 |

**E. 数据污染风险说明**

- 原始评测数据集能否用于训练 → ❌ 通常不能
- 如何用管线生成不重叠的新数据 → ✅ 改 seed / 参数
- 生成数据的多样性保障机制（模板、随机化、组合爆炸）

**F. 实际使用建议**
- 第一步做什么（快速验证管线能跑通）
- 批量生成的规模建议
- 成本估算（API 调用量 / 时间）

## 报告写作规范

### 格式要求

- 使用**中文**撰写整体文档
- 英文术语首次出现时附上英文（如"问题解决（Issue Resolving）"）
- 代码/配置引用保持英文原文
- **多用表格**对比呈现数据，避免大段纯文本
- 目录结构使用代码块，关键文件展示完整或摘要内容
- 适当使用视觉元素（`→` `↓` 流程图箭头，`✅` `❌` 状态标记，`⚠️` 注意事项）

### 内容优先级

```
必写（必须有）         ⭐⭐⭐  Benchmark 背景、数据集介绍、评估方法、结果
强烈推荐（尽量有）     ⭐⭐    目录结构、任务示例、构建流程
锦上添花（有则更佳）   ⭐     数据用途分析、人工/AI 分工、扩展想法
```

### 获取数据的工具方法

- `read_file(path)` — 读取文件内容（PDF、代码、配置等）
- `list_dir(path)` — 列出目录内容
- `search_file(pattern, recursive=true)` — 按文件名搜索（如 `task.yaml`、`*.json`）
- `search_content(pattern, path)` — 按内容搜索（如特定类名、函数名）

## 注意事项

1. **不要逐字翻译论文**：调研报告的目的是**提炼和组织**，不是翻译。每个内容块要有自己的结构和重点。

2. **表格优于列表**：能放进表格的数据就不要用散列表述。表格的"对比感"远强于列表。

3. **示例要真实**：任务/样本示例要从仓库中实际读取，不要编造或伪造。

4. **区分事实与推理**：
   - 论文/仓库中的内容 → 直接引用并标注来源
   - 自己推理的内容（如"轨迹数据可用于 DPO 训练"）→ 用"可"、"建议"等措辞区分

5. **版本一致性**：仓库内容可能与论文不完全一致（如仓库已更新），应同时标注论文数据与仓库实际数据。

6. **灵活裁剪**：无需生搬硬套全部 10 个内容块。根据可用的输入材料灵活决定哪些详细写、哪些简写、哪些跳过。
